## What actually helps

1. Keep the GitHub repository public with a clear, relevant About description, high-quality topics, and an accurate README that answers developer questions.
2. Replace preview-only, login-gated or dead outbound URLs with working public destinations.
3. Link to the canonical GitHub repository from genuine external sources users already visit: accurately maintained open-source directory entries, a public documentation/landing site if approved, existing legitimate profiles, and real technical demonstrations.
4. Use meaningful link text such as `Tetherplane — MCP computer control`; avoid spam, fabricated reviews, link farms or paid backlink schemes.
5. Measure branded organic discovery and verified installations separately. Search snippets, stars, views and clicks do not prove onboarding.
6. Keep release status accurate. Public documentation must not imply unsigned developer betas are signed production installers.

## Ranking measurement method

- Record date, country/city, device, language, query, organic rank (not ads), title, target URL, and whether the exact repository URL appears.
- Prefer authenticated Google Search Console when operating a **verified property you own**. A `github.com` repo path is generally not your own Search Console property, so do not attempt to verify or request indexing of GitHub's domain as if you controlled it.
- Use an independently reproducible rank tool or manual non-personalized checks for the GitHub URL; distinguish sample SERPs from Google's authoritative index status.
- Recheck after search crawlers have had time to process changes (typically days to weeks). Google does not guarantee indexing or a top position.
- If a verified public documentation site is approved later, use its own Google Search Console property and submit a sitemap for that site, linking prominently to the canonical GitHub repository.
