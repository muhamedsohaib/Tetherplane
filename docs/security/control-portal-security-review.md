## 1. Executive Summary

The hardening work on `feat/universal-permissions-control-portal` closes the P0/P1/P2 Control Portal issues identified earlier in the branch:

- DOM XSS vectors in the portal UI were eliminated via strict DOM node creation (`textContent`), enforced by automated adversarial Chromium tests ([`tests/e2e/portal-security-browser.test.ts`](../../tests/e2e/portal-security-browser.test.ts)).
- Bearer tokens were removed from URL query parameters (HTTP `400` rejection) and client storage (`localStorage`/`sessionStorage`), replaced by `HttpOnly; SameSite=Strict` cookies exchanged over `POST /portal/api/session` with SHA-256 hashed CSP (`default-src 'none'`), explicit CSRF header verification, and SSE session teardown.
- Capability catalogs were reconciled to all **49 canonical operations** across the 6 Compact MCP tool families (`device`, `files`, `process`, `browser`, `desktop`, `batch`), with monotonic policy revision enforcement on both the relay and local `tetherd` runtime.
- Headless Windows UI Automation failures were decoupled cleanly without forging capability availability, preserving genuine interactive UIA checks while allowing device health, policy sync, process, and browser telemetry to function.

However, source inspection identified **7 verified security/hardening findings** (1 High, 1 Medium-High, 2 Medium, 2 Low-Medium, 1 Low design tradeoff) that remain in the code as committed at `1c2f614`, which are cleanly separated below from **5 theoretical / operational concerns**.

## 2. Domain-by-Domain Verification Matrix

### 2.1 Authentication & Transport Binding

- **Static & OIDC Relay Clients**:
  - [`StaticClientAuthenticator`](../../relay/src/auth/static-auth.ts#L17-L46) stores only SHA-256 hashes of bearer tokens in memory and [`parseClient`](../../relay/src/cli-config.ts#L161-L165) rejects raw tokens inside auth JSON config files (requiring `token_env` indirection).
  - [`OidcClientAuthenticator`](../../relay/src/auth/oidc-auth.ts#L31-L189) enforces HTTPS `issuer`, `audience`, and `jwksUri`, `RS256`, required `exp`/`sub` claims, required configured scopes, exact agreement between `azp` and `client_id` when both appear, and explicit binding/subject-prefix mapping without trusting caller-supplied account/principal claims.
- **Device WebSocket Authentication**:
  - [`DeviceWebSocketGateway`](../../relay/src/devices/ws-gateway.ts#L98-L117) and [`DeviceRegistry.authenticateDevice`](../../relay/src/devices/registry.ts#L115-L140) authenticate devices via `Authorization: Device <secret>` + `x-tetherplane-device-id`, enforce secret length `>= 16`, verify SHA-256 digest using `timingSafeEqual`, reject revoked bindings (`revokedAt !== null`), and terminate superseded (`4000`) or revoked (`4001`) WebSockets cleanly.
  - `tetherd` requires `wss://` by default and permits `ws://` only with explicit loopback flag [`--relay-allow-insecure-localhost`](../../agent/tetherd/src/relay_ws.rs#L60-L71).
- **MCP Session Identity Binding**:
  - [`RemoteMcpHttpGateway`](../../relay/src/mcp/http-gateway.ts#L147-L168) binds each `mcp-session-id` to the initializing `ClientIdentity` (`sameIdentity`), returning HTTP `403` on cross-identity reuse on both POST and GET/DELETE handlers ([lines 234-244](../../relay/src/mcp/http-gateway.ts#L234-L244)).
- **Browser Extension Local Bridge**:
  - [`startExtensionPairingBroker`](../../browser/bridge/src/pairing.ts#L42-L99) listens only on `127.0.0.1`, restricts CORS and `POST /pair` to `Origin: chrome-extension://<32-char-id>` matching `body.extension_id` (and pinned [`browser-extension.id`](../../scripts/browser-extension-host.ts#L117-L135)), and enforces single-use pairing (`410 pairing_consumed`).
  - [`startExtensionBridgeServer`](../../browser/bridge/src/extension-session.ts#L128-L169) authenticates the `hello` handshake and closes (`4003 sensitive_data_forbidden`) on cookie, password, or authorization-header keys.
  - *Residual weaknesses in loopback auth and pairing authorization are recorded in **F-1, F-2, F-5, F-6** below.*

### 2.2 CSRF, XSS, Content Security Policy & Browser Headers

- **Zero Inline HTML Sinks**: [`portal-ui.ts`](../../relay/src/portal/portal-ui.ts#L654-L683) constructs all dynamic DOM nodes via `createEl()` (`createElement`, `.textContent`, `dataset`), with no `innerHTML` / `outerHTML` / `insertAdjacentHTML` / `eval` sinks.
- **Strict CSP & Hardening Headers**: [`PORTAL_CONTENT_SECURITY_POLICY`](../../relay/src/portal/portal-ui.ts#L1688-L1698) sets `default-src 'none'`, SHA-256 hashes for inline script and stylesheet, `connect-src 'self'`, `img-src 'self' data:`, `form-action 'self'`, `frame-ancestors 'none'`, `base-uri 'none'`, `object-src 'none'`. [`RelayControlHttpGateway`](../../relay/src/devices/control-http.ts#L120-L131) adds `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy: same-origin`, and `Cross-Origin-Resource-Policy: same-origin`.
- **CSRF Defense**: Non-GET/HEAD portal API calls require both [`#verifySameOriginHeaders`](../../relay/src/devices/control-http.ts#L818-L860) (`Sec-Fetch-Site !== cross-site`, `Origin`/`Referer` host+protocol checks) and constant-time `X-Tetherplane-Csrf` validation against the server session secret ([lines 755-766](../../relay/src/devices/control-http.ts#L755-L766)), including authenticated CSRF checks on `/portal/api/session/logout` when an active cookie exists ([lines 274-284](../../relay/src/devices/control-http.ts#L274-L284)).
  - *Reverse-proxy TLS caveat on `#verifySameOriginHeaders` and cookie flags is recorded in **F-3** below.*

### 2.3 Session Handling

- **No URL Query Tokens or Client Storage**: [`hasQueryTokenParameter`](../../relay/src/devices/control-http.ts#L872-L886) rejects `token`, `access_token`, `bearer`, `auth`, and `authorization` query parameters on `/portal` and `/portal/*` with HTTP `400` ([lines 99-114](../../relay/src/devices/control-http.ts#L99-L114)). Client login [`connectSession`](../../relay/src/portal/portal-ui.ts#L864-L892) clears the password input before issuing `POST /portal/api/session` with `Authorization: Bearer ...`, keeping CSRF token strictly in closure memory.
- **Cookie Security Attributes & Teardown**: [`formatSessionCookieHeader`](../../relay/src/devices/control-http.ts#L903-L919) issues `HttpOnly; SameSite=Strict; Path=/portal; Max-Age=28800` (with `Secure` appended when direct TLS is enabled on the relay). Sessions use 256-bit random IDs (`randomBytes(32)`), cap at `MAX_PORTAL_SESSIONS = 256`, expire after 8 hours, and immediately terminate associated `/portal/api/events` SSE sockets on logout ([lines 278-283](../../relay/src/devices/control-http.ts#L278-L283)) or expiry ([lines 561-583](../../relay/src/devices/control-http.ts#L561-L583)).

### 2.4 Principal Isolation & Dual-Layer Enforcement

- **Relay Identity Pinning**: [`DeviceRouter.call`](../../relay/src/routing/device-router.ts#L203-L211) overwrites caller-supplied `principal_id` and `actor` from the authenticated `ClientIdentity` (`principal_id: identity.principalId`, `actor: { id: identity.clientId, kind: "ai_client" }`), preventing client spoofing inside tool arguments.
- **Local `tetherd` Authority Boundary**: [`AgentRuntime::execute`](../../agent/tetherd/src/runtime.rs#L385-L388) binds `bound_principal_id` if launched with `--principal-profile`, and [`LocalPolicyBroker::evaluate_synchronized_policy`](../../agent/tether-core/src/policy.rs#L235-L345) independently evaluates synchronized policies (`emergency_lockdown`, [`resolve_principal`](../../agent/tether-core/src/principal.rs#L251-L262), device match, explicit denies, family/op grants, principal `allowed_roots`, global `allowed_directories`, and human-origin process termination) before executing any provider action. Unregistered principals fail closed on both relay (`PolicyStore.evaluateAndRecordInvocation`) and `tetherd`.
  - *Relay owner classification and operator-ID collision gaps are recorded in **F-1, F-2, F-4** below.*

### 2.5 Default Universal Permissions & Explicit Overrides

- **Owner Default at Pairing**: [`ensureDevicePolicy`](../../relay/src/policy/policy-store.ts#L487-L542) and [`SynchronizedDevicePolicy::universal_for_owner`](../../agent/tether-core/src/principal.rs#L228-L248) assign `revision: 1`, `profile_id: "universal"`, `universal_permissions: true`, and all 6 families (`device`, `files`, `process`, `browser`, `desktop`, `batch`) to owner-paired devices.
- **Explicit Deny Precedence**: Both [`evaluatePermissionSet`](../../relay/src/policy/policy-store.ts#L385-L412) and [`PrincipalPermissionSet::evaluate_capability`](../../agent/tether-core/src/principal.rs#L169-L203) evaluate `denied_capabilities` first and `denied_families` second — overriding `universal_permissions`, `allowed_capabilities`, and `allowed_families`.
- **Canonical Schema Integrity**: [`CANONICAL_OPERATIONS_BY_FAMILY`](../../relay/src/policy/policy-store.ts#L25-L85) enumerates 49 verified MCP operations (phantom ops such as `filesystem.delete` remain absent).
- **Human Resource Protection**: Human-origin `process.terminate` stays unconditionally blocked ([`policy.rs:375-386`](../../agent/tether-core/src/policy.rs#L375-L386)), and background coexistence continues to protect unshared human tabs/windows ([`desktop_provider`](../../agent/tetherd/src/runtime.rs#L128-L160), [`browser/bridge`](../../browser/bridge/src/rpc-server.ts)).

### 2.6 Policy Revision Monotonicity & Rollback Security

- **Strictly Increasing Revisions**: All relay mutations (`updateDevicePolicy`, `upsertOperatorPolicy`, `removeOperatorPolicy`, `rollbackDevicePolicy`) compute `nextRevision = Math.max(desiredRevision, appliedRevision ?? 0) + 1` ([`policy-store.ts:753-754, 881-882, 948-949, 1019-1020`](../../relay/src/policy/policy-store.ts#L753-L754)).
- **Forward-Only Rollback**: Rolling back selects an immutable historical snapshot (with `rev 1` per-device baseline preserved indefinitely across `MAX_RECENT_SNAPSHOTS_PER_DEVICE = 120` pruning at [`retainSnapshotsForPersistence`](../../relay/src/policy/policy-store.ts#L1656-L1681)) and mints a **new higher monotonic revision**, preventing stale policy replay.
- **Agent Anti-Rollback & Durable Persistence**: [`AgentRuntime::validate_synchronized_policy`](../../agent/tetherd/src/runtime.rs#L260-L346) rejects `revision == 0`, mismatched `device_id`, `revision < existing.revision`, and conflicting payloads at `revision == existing.revision`, returning `policy_ack { applied: false, currentRevision }` ([`relay_ws.rs:250-278`](../../agent/tetherd/src/relay_ws.rs#L250-L278)). Policies persist atomically via temp file + `sync_all` + `rename` into `<state_dir>/policy/synchronized-policy.json` ([`runtime.rs:462-513`](../../agent/tetherd/src/runtime.rs#L462-L513)). Reconnect via `device_hello` does not push backward when device revision exceeds relay desired revision ([`policy-store.ts:600-620`](../../relay/src/policy/policy-store.ts#L600-L620)).

### 2.7 Emergency Lockdown Security

- **Pre-Emptive Enforcement**: `emergency_lockdown == true` is checked before principal resolution, universal grants, and allowed operations on both the relay ([`policy-store.ts:1091-1120`](../../relay/src/policy/policy-store.ts#L1091-L1120)) and local `tetherd` ([`policy.rs:240-251`](../../agent/tether-core/src/policy.rs#L240-L251)), blocking owner and operator access across all 6 families and persisting across device restarts.
- **Confirmed Invocation & Recovery**: Both [`POST /portal/api/global/apply`](../../relay/src/devices/control-http.ts#L352-L361) and [`POST /portal/api/global/emergency-revoke`](../../relay/src/devices/control-http.ts#L382-L391) require `confirm: true`. Recovery requires either explicit `restore: true` (`Lift Lockdown`), per-device profile application with `emergencyLockdown: false`, or snapshot rollback.

### 3.2 Theoretical / Operational Concerns (Separate from Verified Source Defects)

1. **T-1 — Relay Plaintext Payload Visibility**: As documented in [`docs/security/remote-plane.md:95-116`](../../docs/security/remote-plane.md#L95-L116) and [`docs/security/threat-model.md:27-30`](../../docs/security/threat-model.md#L27-L30), the relay terminates client HTTPS and device WSS connections and forwards plaintext canonical invocations/results without an end-to-end payload encryption layer. Self-hosting and infrastructure isolation mitigate exposure.
2. **T-2 — Ephemeral In-Memory Portal Sessions**: `#portalSessions` lives solely in Node process memory (`MAX_PORTAL_SESSIONS = 256`, FIFO eviction on overflow at [`control-http.ts:789-793`](../../relay/src/devices/control-http.ts#L789-L793)). Relay restarts log out all portal browsers, and horizontal scaling without sticky sessions/shared session storage would fail session validation.
3. **T-3 — Equal-Privilege OS Malware (Out of Scope)**: Consistent with [`docs/security/threat-model.md:31-38`](../../docs/security/threat-model.md#L31-L38), loopback TCP endpoints (`17657`), token files, and `synchronized-policy.json` assume OS-user account isolation and do not defend against malicious code already running with equal or higher OS privileges under the same Windows user.
4. **T-4 — MV3 Extension Restart Session Lifetime**: Because [`extension/browser/src/background.ts`](../../extension/browser/src/background.ts#L28-L35) intentionally keeps the launch token in `chrome.storage.session` rather than persistent storage on disk, closing Chrome completely requires re-pairing via the popup (`Pair with local Tetherplane`), whereas service-worker idle sleep reconnects automatically.
5. **T-5 — Staging vs. Production Host Collision**: Running default scripts such as [`scripts/live-acceptance.mjs`](../../scripts/live-acceptance.mjs), [`scripts/install-authenticated-browser-windows.ps1`](../../scripts/install-authenticated-browser-windows.ps1), or [`scripts/install-windows.ps1`](../../scripts/install-windows.ps1) on a machine that already hosts production Tetherplane agents would overwrite `%LOCALAPPDATA%\Tetherplane` tokens/binaries, bind production ports `17656–17658`, or touch `HKCU\...\Run` / Scheduled Tasks. Staging acceptance **must** follow the isolated procedure in [`windows-staging-acceptance.md`](../release/windows-staging-acceptance.md).
